# `.otoxan/context.md` Specification

> Canonical spec for the per-install context file read by otoxan agents and workers at startup.  
> Reference: DS-8  
> Status: Draft

---

## 1. Purpose

`~/.otoxan/context.md` is a single Markdown file that provides every otoxan agent and worker with the operating context they need to function correctly within a specific installation. It consolidates what Hermes spread across `SOUL.md`, `MEMORY.md`, and `CLAUDE.md` into one schema-defined artifact with explicit sections, loading rules, and consumer contracts.

The file answers: **Where am I, what am I, what do I have access to, and what are my rules?**

---

## 2. Design Principles

1. **Single file, single source of truth.** One file per install. No supplementary `.md` files, no sidecar JSON. If an agent needs context, it reads this file.
2. **Human-editable, machine-parsed.** Markdown with a defined section structure. Agents parse by heading hierarchy, not by custom syntax.
3. **Installed by `otoxan init`, never overwritten on update.** Same invariant as `config.yaml`: created once, preserved across `otoxan update` and `otoxan init --force`.
4. **Agent-agnostic payload.** The file describes the *install* (platform, stores, rules), not a specific agent persona. Agent identity comes from the identity manifest in MongoDB (`otoxan_global.identities`), not from this file.
5. **No secrets.** No connection strings, tokens, or credentials. Those live in `config.yaml`, environment variables, or Infisical — never in a plain-text Markdown file.

---

## 3. File Location and Resolution

The file location follows the same resolution path as all otoxan config:

```
$OTOXAN_HOME/context.md
```

Default: `~/.otoxan/context.md`

If the file does not exist, agents MUST log a warning and proceed with defaults (empty context). No fatal error.

---

## 4. Section Schema

The file is divided into sections by `##` headings. Each section has a defined purpose and format. Sections MUST appear in the order listed below. Unknown sections are ignored (forward-compatibility).

### 4.1 Required Sections

| # | Heading | Purpose | Format |
|---|---------|---------|--------|
| 1 | `# Otoxan Context` | File header and metadata. | Single `#` heading. First line of the file. |
| 2 | `## Platform` | Install identity: machine name, install path, otoxan version, entry mode. | Key-value pairs in a Markdown table. |
| 3 | `## Architecture` | System layers and component map. Agents use this to know what services exist. | Prose + bullet list. |
| 4 | `## Data Layout` | Where data lives (MongoDB databases, collections). Agents use this to target queries. | Markdown table mapping domain → database → collection. |
| 5 | `## Rules` | Operating invariants and behavioral constraints. Agents MUST obey these. | Numbered list of imperative rules. |
| 6 | `## Tools` | Available MCP servers and their domains. | Markdown table: binary → domain → tools. |
| 7 | `## Paths` | Filesystem paths the agent may need. | Key-value table. |

### 4.2 Optional Sections

| # | Heading | Purpose | Format |
|---|---------|---------|--------|
| 8 | `## Memory` | Persistent lessons, bug history, architectural decisions specific to this install. | Bullet list with date-prefixed entries (`YYYY-MM-DD: ...`). |
| 9 | `## Agents` | Known agents on this install and their roles. | Markdown table: name → role → notes. |
| 10 | `## Custom` | Freeform install-specific context. | Unstructured Markdown. |

## 5. Section Contents (Normative)

### 5.1 `# Otoxan Context`

```markdown
# Otoxan Context

> Auto-generated by `otoxan init` on {DATE}.
> Edit freely. Agents read this file at startup.
```

The `#` heading MUST be the first line. The blockquote is a comment for human editors.

### 5.2 `## Platform`

```markdown
## Platform

| Key | Value |
|-----|-------|
| hostname | `silas-workstation` |
| otoxan_home | `~/.otoxan` |
| entry_mode | `local` |
| mongo_db | `otoxan` |
| version | `0.3.1` |
```

Populated by `otoxan init` from runtime detection. Agents read `hostname` for log disambiguation, `entry_mode` for session behavior, and `version` for capability gating.

### 5.3 `## Architecture`

```markdown
## Architecture

Three-layer system:

- **Foundation** — `autozan-go-foundation`: MongoDB connectivity, soft-delete wrappers, logging, config.
- **Stores** — MongoDB-backed document stores (tasks, plans, teams, flows, memory, knowledge, directives, reports, notifications). Per-agent database isolation.
- **Dispatch** — Goroutine-based task dispatcher: ensure, claim, reap, reclaim, spawn. In-memory coordination, MongoDB for durable state.

Runtime services (local mode):
- MongoDB — primary data store
- Qdrant — vector search (memory, knowledge)
- Dispatch daemon — task execution orchestrator
- MCP servers — stdio JSON-RPC tool servers per domain
```

### 5.4 `## Data Layout`

```markdown
## Data Layout

All durable state in MongoDB. No on-disk state under `~/.otoxan/` except this file, `config.yaml`, `version`, logs, and cache.

| Domain | Database | Collection | Notes |
|--------|----------|------------|-------|
| tasks | `otoxan_agent_{name}` | `tasks` | Per-agent isolation |
| plans | `otoxan_agent_{name}` | `plans` | Per-agent isolation |
| directives | `otoxan_agent_{name}` | `directives` | Per-agent isolation |
| reports | `otoxan_agent_{name}` | `reports` | Per-agent isolation |
| flows | `otoxan_agent_{name}` | `flows` | Per-agent isolation |
| memory | `otoxan_agent_{name}` | `memory` | Metadata; vectors in Qdrant |
| teams | `otoxan_global` | `teams` | Cross-agent |
| identities | `otoxan_global` | `identities` | Cross-agent personas |
| notifications | `otoxan_global` | `notifications` | Cross-agent |
| dispatch_requests | `otoxan_agent_{name}` | `dispatch_requests` | Transient dispatch state |
| dispatch_spawns | `otoxan_agent_{name}` | `dispatch_spawns` | Spawn tracking |
| task_events | `otoxan_agent_{name}` | `task_events` | Event log |
| task_counters | `otoxan_agent_{name}` | `task_counters` | Aggregate counters |
```

### 5.5 `## Rules`

```markdown
## Rules

1. **MongoDB is canonical.** All durable state lives in MongoDB. No `*.json`, `*.db`, `*.sqlite` state files. If you need to persist it, write to a store.
2. **Soft-delete only.** Never hard-delete user data. Set `deleted: true`, `deleted_at`, `deleted_by`. Soft-deletes are recoverable; hard-deletes are not.
3. **No secrets in files.** Credentials live in `config.yaml`, environment variables, or Infisical. Never write tokens, URIs, or passwords to this file or any Markdown file.
4. **Respect task status.** Tasks in QUEUED, RUNNING, CLAIMED, PENDING_REVIEW, or BLOCKED are live queue state. Do not modify, delete, or dedupe them based on agent judgment.
5. **Plans live in MongoDB.** The dashboard reads from MongoDB only. A plan on disk is invisible.
6. **Obey identity routing.** Agent identity comes from the identity manifest in `otoxan_global.identities`, not from hostname, git config, or session defaults.
7. **Test = production.** When testing automated work, match model, skills, code paths, and data stores.
8. **Verify, don't should.** After every write/save, read it back. State the count as evidence.
9. **Report completion.** Every dispatched task MUST write a completion marker (`/tmp/dispatch_completed/{task_id}.json`) even on failure.
10. **No on-disk state.** The only files under `~/.otoxan/` are: `context.md`, `config.yaml`, `version`, `logs/`, `cache/`, `bin/`, `run/`. Everything else belongs in MongoDB.
```

### 5.6 `## Tools`

```markdown
## Tools

MCP servers available on this install (stdio JSON-RPC):

| Binary | Domain | Tools |
|--------|--------|-------|
| `otoxan-mcp-tasks` | Tasks | create, get, list, update, delete |

```

### 5.7 `## Paths`

```markdown
## Paths

| Path | Purpose |
|------|---------|
| `~/.otoxan/` | Install home (`$OTOXAN_HOME`) |
| `~/.otoxan/bin/otoxan` | Main binary |
| `~/.otoxan/config.yaml` | User configuration |
| `~/.otoxan/version` | Installed version string |

```

### 5.8 `## Memory` (Optional)

```markdown
## Memory

Install-specific lessons and decisions. Append-only. Date-prefix every entry.

- 2026-05-13: Initial context.md created by `otoxan init`.
```

This section replaces the Hermes `MEMORY.md` pattern. It is append-only: agents read it for context but should only append, never rewrite historical entries.

### 5.9 `## Agents` (Optional)

```markdown
## Agents

Known agents on this install. Identity details come from `otoxan_global.identities`; this table is for quick reference only.

| Agent | Role | Notes |
|-------|------|-------|
| xander | admin | Primary system administrator |
| default | general | Default agent for unspecified routing |
```

### 5.10 `## Custom` (Optional)

Freeform Markdown. Install-specific context that doesn't fit the schema above. Agents treat this as advisory, not normative.

## 6. Generation

### 6.1 By `otoxan init`

`otoxan init` generates `context.md` with:

1. The `# Otoxan Context` header with current date.
2. The `## Platform` section populated from runtime detection.
3. The `## Architecture`, `## Data Layout`, `## Rules`, `## Tools`, and `## Paths` sections with standard defaults.
4. An empty `## Memory` section with the creation date entry.
5. No `## Agents` or `## Custom` sections (user adds if needed).

### 6.2 On `otoxan init --force`

Same as `otoxan init` but:
- If `context.md` already exists, it is **not overwritten** (same invariant as `config.yaml`).
- Print a message: `context.md already exists; skipping (edit manually or delete to regenerate)`.

### 6.3 Manual editing

Users and agents may edit `context.md` at any time. Changes take effect on next agent startup (agents read the file once at startup, not on every request).

---

## 7. Loading Rules

### 7.1 When agents read it

| Consumer | When | How |
|----------|------|-----|
| `otoxan` CLI | `PersistentPreRunE` in root command | Read full file, parse sections, inject into command context |
| `otoxan-worker` | After MCP `initialize` | Read full file, include in system prompt |
| `otoxan-dispatch` | At daemon startup | Read `## Platform` and `## Data Layout` for routing |
| Xander (agent) | At session start | Read full file, merge with identity manifest system prompt |

### 7.2 Parse contract

1. Read the entire file as UTF-8 text.
2. Split on `## ` headings. Each section is the text between two `## ` headings.
3. Match section title to the schema. Unknown sections are kept but not interpreted.
4. Tables are parsed as standard Markdown tables (pipe-delimited, header row + separator row + data rows).
5. If a required section is missing, log a warning and use defaults. No fatal error.

### 7.3 Injection into agent context

The file content is injected into the agent's context as-is (raw Markdown). It is NOT wrapped in JSON, base64, or any other encoding. The agent's system prompt or context assembly layer decides where to place it relative to the identity manifest.

Recommended injection order for a worker's system prompt:

```
1. Identity manifest (from MongoDB) — who I am
2. context.md — where I am and what the rules are
3. Task prompt (from dispatch) — what I need to do
```

## 8. Relationship to Other Artifacts

| Artifact | Location | Relationship |
|----------|----------|--------------|
| `config.yaml` | `~/.otoxan/config.yaml` | Config holds secrets and connection details. Context holds rules and architecture. They are complementary and never overlap. |
| Identity manifest | `otoxan_global.identities` | Identity defines *who* the agent is (persona, system prompt, provider config). Context defines *where* the agent runs (platform, data layout, rules). Both are injected at startup. |
| `SOUL.md` (Hermes) | `~/.hermes/profiles/{name}/SOUL.md` | Superseded. In otoxan, persona is an identity manifest in MongoDB, not a file on disk. |
| `MEMORY.md` (Hermes) | `~/.hermes/memories/MEMORY.md` | Superseded by the `## Memory` section of context.md. |
| `CLAUDE.md` (Hermes) | `~/.hermes/CLAUDE.md` | Superseded. Operating instructions for agents are in `## Rules`. Codebase-specific guidance lives in product repos. |
| Store specs | `otoxan/docs/*.md` | Context.md summarizes the store inventory. Full schemas stay in `docs/`. Agents that need field-level detail should read the doc files directly. |

## 9. Size and Performance

- **Expected size:** 2–5 KB (standard install). May grow with `## Memory` entries.
- **Hard limit:** 32 KB. If the file exceeds 32 KB, agents MUST log a warning suggesting the user prune `## Memory` or `## Custom`.
- **Parse time:** Under 1 ms for a 5 KB file. No caching needed — read once at startup.

---

## 10. Migration from Hermes

When migrating from a Hermes install (`~/.hermes/`) to otoxan (`~/.otoxan/`):

1. `otoxan init` creates `context.md` with standard defaults.
2. A migration script (future: `otoxan migrate-context`) can extract:
   - Key rules from `~/.hermes/CLAUDE.md` → `## Rules`
   - Bug history from `~/.hermes/memories/MEMORY.md` → `## Memory`
   - Agent list from `~/.hermes/profiles/` → `## Agents`
3. Identity manifests are migrated separately by `xander migrate-schema`.
